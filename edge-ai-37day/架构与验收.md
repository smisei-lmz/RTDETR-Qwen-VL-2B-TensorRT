# 架构、实现契约与最终验收

> 本文描述迁移前已有实现。新版目标与最终验收以 [6个大任务计划](每日开发路线.md) 为准：运行时迁移至C++/llama.cpp，DMA-BUF/EGL改为选做；下文旧版板端共享链路清单用于扩展实验。


## 1. 开发目标

先建立可解释、可验证的 PC 异步感知系统，再把输入替换为板端相机共享内存。主线要解决的是帧身份、内存所有权、异步完成、过载、新鲜度和资源竞争。模型训练、相机驱动、SLAM、导航和机械控制不作为本项目的前置条件。

分三种运行后端：`cpu` 为可控红色区域教学算法；`cuda` 为真正执行 GPU kernel 的教学算法；`trt` 为真实 RT-DETRv2-S 推理。前两者用来验证系统行为，不能作为神经网络推理成绩。

## 2. 数据流及每次内存变化

### PC 路径

```text
文件/合成输入 → CPU Image Pool[slot, generation]
→ 有界 Ready Queue（只传 lease 和 metadata）
→ scheduler 选择空闲 lane
→ CPU 图像复制到该 lane 的 pinned host buffer
→ CPU Image Pool 归还
→ 同一 CUDA stream：H2D → 独立 device RGB → 双线性拉伸/RGB NCHW tensor
→ TensorRT（含 sigmoid/top-k）→ [1,300,6] D2H → CPU过滤/坐标还原
→ JSONL结果 → ROS bridge → DetectionFrame
```

PC 有独立显存，当前路径明确存在 H2D；输入回放使用已解码 PPM，视频解码耗时不包含在检测指标中。`pinned buffer` 的存活时间长于原始 CPU slot：`submit()` 复制完原始图像即可归还 CPU slot，但 lane 内 pinned、device RGB、tensor、输出仍需等完成事件。异步并不意味着可以提前覆盖 pinned 内存。

### Jetson 路径

```text
NvBufSurface 分配兼容 surface
→ bufferDesc(fd) 通过 V4L2_MEMORY_DMABUF QBUF 给相机驱动
→ 相机写入 YUYV/NV12 → DQBUF 后主机获得该帧
→ EGLImage/CUDA 映射得到经过校验的 device plane/texture
→ CUDA 读源 YUV、写本 lane 独立 RGB
→ source_done event 完成 → 原相机 fd 可重新 QBUF
→ 独立 RGB → 模型输入 tensor → TensorRT → 结果
```

相机缓冲区和模型输入是**两个用途不同的池**。颜色格式、尺寸、stride、布局改变时，通常需要独立输出内存；它未必需要导出 fd。TensorRT 读取的是已绑定的 CUDA tensor 地址，不是随便一个 DMABUF fd。

对应你之前的 RKSoC 问题：Camera 的 fd 常作为 RGA 输入，RGA 的 resize/色彩变换通常写入另一个兼容目标 buffer；该目标是否可以直接作为 RKNN 输入，取决于 RGA/RKNN 的 allocator、格式、stride 和外部内存接口。Jetson 在这里用 CUDA 读共享源并写 tensor/RGB，概念相似，接口不同。**fd 是共享内存句柄，不是像素地址，也不是设备完成信号。**

本项目特意提供 Day32 拷贝基线、Day33 相机导出能力探针、Day34 NVIDIA 分配→相机导入的共享路径。EXPBUF 成功不能证明 CUDA 支持导入该 exporter；V4L2 导入能力也不能从“自带 ISP”推断。具体硬件不支持时要报告能力边界。

### VLM 路径

每秒最多约一张独立 RGB 缩略图（默认最大宽640）→ base64 PPM → bridge 转 JPEG → ROS Snapshot → coordinator 缓存最新快照 → AnalyzeScene Action → Qwen 视觉编码器与文本生成 → 带身份的 SceneAnswer。

板端共享模式在请求快照时会额外复制 RGB 到 host，再生成缩略图；检测结果走图内 top-k 输出→host。当前并未实现全 GPU JPEG 编码或 GPU tensor 的跨进程 ROS 零拷贝。VLM 图像小、频率低，便于先正确隔离生命周期；质量不足时调整分辨率并重新测量。

## 3. 线程和进程

| 执行单元 | 职责 | 可阻塞的位置 | 不能做的事 |
|---|---|---|---|
| PC capture thread | 填空闲 slot、发布 lease、队列满时移除旧待处理帧 | 文件读取、输入节拍 | 修改 READING slot |
| PC scheduler/main | 选择 lane、提交 GPU、轮询事件、回收结果 | 小间隔等待、结果输出 | 依据 sleep 猜 GPU 完成 |
| CUDA stream × lane | 顺序执行拷贝/预处理/推理/解码 | 设备调度 | 跨 lane 复用可写 tensor/context |
| Jetson main loop | DQBUF、提交、source event 检查、QBUF | poll 最多数毫秒 | 未完成读取就 QBUF |
| ROS bridge reader thread | 持续排空子进程 stdout、替换最新结果槽 | 管道读取 | 无界积压图片 |
| ROS bridge executor | 组消息、JPEG 编码、发布 | 编码 | 让 VLM 持有相机 lease |
| coordinator process | 最新快照、问题、单个活动请求、取消 | ROS 回调 | 把旧答案当新画面的答案 |
| VLM server process | 模型加载、一次一个请求、反馈和结果 | 模型推理 | 将取消确认当 GPU 已立即空闲 |

不为每个 kernel 建线程；CPU 线程负责提交，GPU stream 负责设备执行。初版用 mutex+condition_variable 的有界队列，便于验证；无锁结构并非必要验收条件。先证明锁确为瓶颈，再考虑替换。

Jetson 当前实现把采集和 GPU 调度放在同一个事件循环。它没有 PC 的 ready 队列与主动 drain-to-latest 逻辑；GPU 饱和时，驱动内部可积压已完成帧。板端延迟优化的后续任务是基于 sequence/driver timestamp 评估新鲜度，再加入受控的 DQBUF 丢旧帧，不能仅看 FPS。

## 4. Buffer 生命周期

| 存储 | 分配时机 | 合法归还/复用点 |
|---|---|---|
| CPU Image slot | 建池，像素 vector 首次填充/尺寸变化时扩容 | submit 完成 CPU读取/独立拷贝后；未提交被丢弃时 |
| pinned host lane | CUDA backend 初始化 | lane done event 与结果回收完成后 |
| GPU RGB/tensor/output | backend 初始化 | 同 lane 上一帧完全结束且结果已消费 |
| V4L2 camera surface | 采集开始前 | GPU 最后一次读源后的 source_done 成功 |
| VLM 快照 | 低频采样时生成独立内容 | Action 与缓存均不再引用时 |

CPU 状态为 `FREE → FILLING → READY → READING → FREE`。每次借用增加 generation；队列记录 `(slot,generation)`，不能仅用 slot 判断是否同一帧。完成 GPU 提交并不代表 GPU 已结束；`submit()` 可以归还的是已经复制出去的 CPU源，不是整个 lane。

Jetson 状态为 `QUEUED_TO_CAMERA → DEQUEUED → GPU_READING → QBUF`。DQBUF 确认该次采集完成，source_done 确认 GPU 不再读取原始相机面。TensorRT 此时可能还没结束，但它读的是独立 RGB/tensor，所以相机面可以提前归还。

所有权设计要点：

- 只丢掉尚未提交、仍由 ready queue 持有的帧。已经提交 GPU 的工作不靠删除队列元素取消。
- fd 属于分配器或 exporter；借用者不能提前 close。代码的 NvBufSurface 生命周期覆盖相机使用和 CUDA mapping。
- EGL 注册、纹理对象、surface 的销毁发生在设备读取结束之后。
- 退出时停止新的输入，排空/停止设备工作，解除映射并销毁 surface，最后关闭设备。异常路径同样由 RAII 管理；不吞掉运行错误后假报成功。

当前参考实现保留部分结果/缩略图分配，因此是固定的原始图像与 tensor 池，不是“热路径完全零分配”。

## 5. 同步与缓存一致性

CPU 线程之间用 mutex/condition_variable 和 atomic 发布状态。CPU/GPU 之间用 CUDA stream 顺序及 `cudaEventQuery`。同一个 lane 的预处理、推理、后处理放在同一 stream，依次观察已写入的数据。每 lane 一个 TensorRT execution context；不并发操作同一 context。

相机与 GPU 的边界采用 V4L2 DQBUF 后才读源、CUDA source_done 后才 QBUF。前提是实际驱动支持被导入 surface 的 DMA/cache 一致性契约；板端验收要验证这一点。本代码没有把 CUDA Event 导出为通用 Linux sync_file fence，也没有自动跨任意设备建立隐式依赖。

CPU 直接访问 NVIDIA surface 的诊断模式通过 `NvBufSurfaceMap` 和 `NvBufSurfaceSyncForCpu`；如果今后改用通用 DMABUF mmap，要依据 exporter 文档用 `DMA_BUF_IOCTL_SYNC` 配对 CPU访问，并另行确保设备作业已完成。cache sync、设备完成和 CPU 线程同步是不同层面的保证。

禁止用 `sleep(预计推理耗时)` 判断完成。sleep 只用于节拍或降低轮询 CPU 占用；结果就绪由事件/驱动接口证明。错误发生时不能把“已提交”当成“已完成”归还内存。

## 6. 时间戳与身份

帧身份采用 `(session_id, frame_id)`；buffer 身份采用 `(slot,generation)`；问答身份采用 `request_id`。session 在启动时重新生成，frame 从零递增；跨主机生产使用时应升级为持久唯一 ID/UUID，当前纳秒启动标记用于单源课程示例。

| 字段 | 来源与用途 | 当前限制 |
|---|---|---|
| captured_mono_ns | steady_clock，源图像获得后打点 | PC 不含文件读取/合成；Jetson 是 DQBUF 后，不是曝光时刻 |
| captured_unix_ns | 同处的 system_clock，用于 ROS header | 会受系统时钟调整影响；跨主机须同步并记录误差 |
| driver_timestamp_ns / driver_flags | V4L2 原始 timestamp 与 flags | 必须结合驱动文档确定 clock 与 SOE/EOF 含义，不能默认曝光时间 |
| CUDA Event ms | 同 stream 事件区间 | 是耗时，不是 Unix 时间，不能与 CPU 时间戳相减 |
| SceneAnswer.source_age_ms | 发布回答时相对快照源时间的年龄 | 依赖系统时钟一致；当前不支持 sim time |

`latency_ms` 为 host 采集打点到结果可消费的时间，包含队列等待和主机回收，未包含 ROS subscriber 接收、相机曝光/驱动排队、视频离线解码。ROS端端到端指标应另外记录订阅接收时刻；真正 sensor-to-result 需确认硬件时钟并建立可验证映射。无法确认时报告 unknown，不能编造“曝光时间”。

VLM 接收目标时检查输入新鲜度，输出时检查答案年龄、活动请求和 frame 身份；超时以 monotonic elapsed 判断。系统时间跳变、跨机时钟偏差必须单独处理，不能把负年龄视作新鲜。

## 7. ROS2 + VLM 的具体协议

| 接口 | 内容 |
|---|---|
| `/perception/detections` | DetectionFrame：同帧框、类别、尺寸、身份、时间戳 |
| `/perception/snapshot` | Snapshot：独立JPEG及该帧的身份和检测信息 |
| `/assistant/question` | 用户问题，std_msgs/String |
| `/assistant/cancel` | 取消当前问题，std_msgs/Empty |
| `/vlm/analyze_scene` | AnalyzeScene Action |
| `/assistant/answer` | SceneAnswer，状态、答案、request/frame、耗时/年龄 |

感知 Topic 使用 KEEP_LAST depth1 + BEST_EFFORT；这是“追求最新”的策略，允许消息丢失。Action 提供请求/反馈/结果/取消。协调器保留最新快照、一个活动请求和一个待处理问题；服务端忙时拒绝新目标，不建立无限请求队列。

先做 Day23 mock 验证通信和生命周期，再在 Day24 跑真实图片理解，Day25 才合并。mock 的输出显式写 MOCK，没有图像理解能力。Qwen 收到的是图片和问题，不是 RT-DETR 的 tensor；检测元数据可作为扩展提示，但不能替代图像。

运行 Day25 后，在另一个已 source 的终端：

```bash
ros2 topic pub --once /assistant/question std_msgs/msg/String "{data: '请描述图像中的主要物体及其位置'}"
ros2 topic echo /assistant/answer
ros2 topic pub --once /assistant/cancel std_msgs/msg/Empty '{}'
```

Day25/30/36 默认开启离席巡检，关闭周期自动提问。ROI 内先确认有人2秒，再连续观测无人10秒，固定触发帧并调用 VLM；人返回、断流和身份变化会使旧事件失效。手工问题仍通过同一 Topic 使用最新快照。图片与事件终态保存在 runs/workstation。规则和场景验收见 [工位巡检场景](工位巡检场景.md)。Action 取消是协作式：推理可在生成步骤检查停止标记，但不能抢占正在执行的 kernel。没有确认停止时服务保持 busy；当前未实现自动重启卡死模型进程的 watchdog。

输出用于观察与解释，不接机器人电机控制。若以后接规划器，应定义可验证结构化意图、时效与执行约束，不能把自然语言回答直接当控制指令。

## 8. 故障处理

| 故障 | 当前行为 | 验收方法 |
|---|---|---|
| CPU pool 无空位 / ready 队列满 | 明确丢帧计数；队列满释放旧未提交 lease | 高输入率 + 慢处理，检查计数守恒 |
| stale lease / 提前归还 | 抛错，拒绝继续读取 | Day11 故障注入 |
| 图片损坏或尺寸越界 | 报错并清理 | 替换一张截断 PPM，观察非零退出 |
| 不兼容模型 / engine | 构建或加载阶段失败 | 错路径/不符合模型契约的输入 |
| CUDA/TRT 提交失败 | 退出，清理已提交设备资源 | 保留 CUDA error，不静默切 CPU |
| 模型输出非 [1,300,6] 或张量名不符 | 加载阶段拒绝 | 旧引擎不能直接替换，必须重新导出 |
| 相机坏帧 | bad_frames 计数，归还该 buffer | 核对 flags 和 bytesused |
| 断开相机 / 5秒无帧 | poll错误或超时报错退出 | 板端手工断流测试 |
| DMABUF布局/导入不支持 | 直接失败，可单独运行 copy 基线 | 能力探针和共享阶段分开记录 |
| VLM busy / timeout / cancel | 明确状态；不发布过期成功答案 | Day26 真实 ROS Action + mock延迟 |
| C++ 子进程退出 | bridge 周期报告错误 | 手工停止 producer 后检查日志 |
| GPU进程迟迟不退出 | 有限等待后强制终止并记录 | 强退不宣称完成优雅资源回收 |

本实现没有自动相机重连、生产级 supervision 或崩溃自动恢复；日程的故障验收包含“失败可见且重启可恢复”，不是无人值守自愈。

## 9. 指标与实验方法

每次实验固定模型、输入尺寸、频率、源数据、精度、lane数量和软件版本。Jetson 另记 nvpmodel、时钟策略、温度、供电、散热。先预热，再统计足够多帧，至少保存 p50/p95/p99、完成数、丢帧数。

| 指标 | 当前测量 |
|---|---|
| latency_ms | host获取图像之后到CPU可消费结果 |
| copy_or_yuv_ms | PC H2D 或 Jetson YUV→RGB CUDA区间 |
| preprocess_ms | 双线性拉伸与NCHW区间 |
| inference_ms | TRT enqueue对应区间；cuda教学后端是颜色算法区间 |
| gpu_post_d2h_ms | RT-DETR输出D2H；top-k计入 inference_ms |
| cpu_ms | CPU后处理或CPU教学算法；不是完整线程占用率 |
| device_ms | 从设备起始到结果事件的整个stream区间 |
| queue_highwater/drop_* | PC队列边界和丢帧原因 |
| all_slots_free / held_sources | 退出时生命周期证据 |

开启预处理校验或板端快照时还有诊断/快照 D2H，计入 device_ms，但不计为 TRT inference_ms，因此各阶段之和可能小于 device_ms。关闭校验后再测正式性能。脚本 `completion_density_per_source_second` 使用源时间跨度，只能作为密度参考；稳态吞吐应另用测量窗口的实际完成数/墙钟时间，有限任务可用 summary 的 elapsed_s 算含起停开销的平均完成率。

课程没有预设“必达120FPS”。建议 Day18 选定一个目标，如输入30fps时 host p99≤100ms，然后以你的实际模型和硬件验证。PC 与板卡分别报告；开 VLM 后要重新量测检测尾延迟。两进程共享GPU仍会争用计算和带宽，并非硬实时隔离。

建议对比矩阵：串行/异步 × 1/2 lanes；queue=1/2/8；VLM关/开；Jetson copy/shared。每次只变一个因素。精度不能只看一张图：单图一致性门槛之外，要跑数据集评估；显式 COCO 标注子集可用于部署回归，真实工位另需独立视频测试集。

内存：原图大小看 stride×height 和实际 plane；模型 tensor 按 shape×dtype；总预算还包括 TensorRT workspace、每lane context、VLM权重/KV cache、ROS/JPEG和系统。不要只加模型权重文件大小就断言可驻留。Jetson 的8GB包含操作系统占用。

## 10. 交付验收表

### PC阶段

- [ ] 真实模型参考、ONNX checker + ORT 数值校验、TRT构建及精度记录。
- [ ] 初始无人、短遮挡、正常离席、返回、断流、忙状态六项场景验收；事件图片和终态可追溯。
- [ ] C++ CPU测试与过载计数守恒，所有slot归还。
- [ ] CUDA预处理最大误差≤0.002，真实TRT框与参考通过一对一校验。
- [ ] ROS Topic与Action实际通信；忙拒绝/取消/超时测试通过。
- [ ] Qwen真实图片理解；图片、问题、答案身份关联正确。
- [ ] TRT单独30分钟稳定性；另有VLM开/关的检测延迟与内存对比。
- [ ] 保存软件版本、命令、结果、失败边界和演示。

### Jetson阶段

- [ ] 现成相机驱动可用，协商格式/stride/颜色矩阵已记录。
- [ ] 拷贝基线与导出能力分别验证。
- [ ] NVIDIA surface成功导入相机；CUDA布局校验、非空源校验通过。
- [ ] source_done后QBUF；关闭时 held_sources=0，无跨帧读写。
- [ ] 板上重建TRT并完成真实检测与精度检查。
- [ ] 板上ROS/VLM实际运行；若改为外部VLM服务，明确标为分布式部署并另做网络/时钟/身份验收，不标为全板端完成。
- [ ] 30分钟检测及另行ROS/VLM并发测试；断流、退出、重新启动记录齐全。
- [ ] 性能报告覆盖尾延迟、吞吐、丢帧、显存/共享内存、温度和功耗模式。

INT8量化、CUDA Graph、硬件解码、跨进程DMABUF fd传递、ROS loaned message、watchdog、自动重连均可作为后续扩展；当前源码与验收不宣称已经实现。
